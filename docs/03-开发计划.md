# 开发计划

> 项目：单位多出口宽带网络监控系统（NetWatch）
> 配套文档：《01-开源项目调研报告.md》《02-系统设计与功能规格.md》
> 估算基准：2 名开发（1 后端 Go + 1 前端 Vue，可兼互备）；1 名网络管理员配合（非全职）

---

## 1. 技术路线结论

- **不采用单一开源项目二次开发**：调研结论是无项目匹配"源网段策略路由探测 + 线路域模型 + 测速调度 + 统一探针管理 + 中文大屏"的组合；以哪吒/夜莺为基座改造的域模型成本不低于自研且与上游割裂。
- **采用"自研轻量平台 + 复用成熟组件"**：自研 Go 探针 Agent 与中心服务（合计预估 1.2~1.5 万行代码），复用 VictoriaMetrics（时序存储）、PostgreSQL、Vue3 前端框架。
- **UI 复用（已确认）**：Uptime Kuma 为 MIT 协议、Vue3 + Bootstrap 5 + Chart.js 同栈，管理端首页按其 Dashboard 设计语言开发并直接复用其组件/样式代码（保留版权声明）。
- **备选降级路线（方案 A）**：若确认阶段希望"零自研代码先跑起来"，可用夜莺 + Categraf(ping) + VictoriaMetrics + Grafana 搭建连通性监测原型（约 3~5 个工作日），仅作为验证期过渡，不作为最终形态。

## 1.1 需求方决议记录（2026-10-25）

1. 策略路由可行性与虚拟化网络权限：✅ 确认可行（M1 保留实施验证）。
2. 线路清单、SMTP：部署后在管理后台录入/填写（首次启动向导，M1 必须交付管理后台）。
3. 测速：探针直接对互联网测速（Ookla 公共节点协议实现 + HTTP 下载测速兜底），全局串行错峰。
4. 探测目标：后台自由配置，默认百度/小米/腾讯/京东等高稳定大站 + 公共 DNS，多目标投票防误判。
5. UI：复用 Uptime Kuma（MIT）首页设计与代码。

## 3. 里程碑详细分解

### M0 工程准备与验证（第 1 周）

任务：
1. **策略路由实施验证**（关键路径）：在任一楼层子网临时接入 1 台测试 VM，验证出站流量确实经该楼层线路公网 IP 出站（`curl ifconfig.me` 验证出口 IP）、跨 VLAN 访问中心端回程正常。（需求方已确认可行，此处为实施验证）
2. 创建 1 台试验探针 VM，验证虚拟化平台端口组/VLAN 接入。
3. 工程骨架：Go 单模块 monorepo（cmd/agent + cmd/server + internal）、Docker Compose（VictoriaMetrics + PostgreSQL + server）、探针 systemd 单元与一键安装脚本。
4. 协议原型：探针最小实现（源 IP 绑定 ping + HTTPS 上报）→ 中心接收 → 入 VictoriaMetrics，端到端跑通。
5. UI 复用评估：拉取 Uptime Kuma（MIT）前端源码，圈定可复用组件清单（Dashboard 卡片、心跳条、主题 SCSS）。

验收标准：验证报告确认 PBR 探测可行；demo 探针数据可在 VictoriaMetrics 查询到；工程骨架编译通过。

### M1 连通性监测 MVP + 管理后台（第 2~4 周）

后端：
- 探针 Agent：ICMP/TCPing/DNS/HTTP 探测（源 IP 绑定）、错峰调度、批量上报、断网本地缓存 24h、自动注册、心跳、配置拉取。
- 中心服务：探针注册/心跳/盲区检测、指标入库（VictoriaMetrics）、P0/P1 告警引擎（线路中断、楼层中断、盲区）、SMTP 模块（HTML 模板、恢复通知、冷却抑制、测试邮件）。
- Docker Compose 编排（VictoriaMetrics + PostgreSQL + 中心服务）。

管理后台（本轮必须交付，因清单/SMTP 均后台填写）：
- 首次启动向导：创建管理员 → SMTP 配置（含测试邮件）→ 楼层/线路录入（手工 + CSV 导入）→ 探针绑定线路。
- 总览仪表盘（12 线路状态卡 + 心跳条，UI 对齐 Uptime Kuma）、线路详情页（实时/历史曲线）、探针管理页（注册/绑定/配置下发）、告警中心（当前/历史 + 规则 + 静默）、系统设置（探测目标库、阈值、用户）。

运维：探针部署一键脚本 + 虚拟化模板制作文档；12 台探针上线。

验收标准：
- 后台录入线路并绑定探针后，12 条线路全部呈现实时状态，数据延迟 < 30s；
- 人为拔断任一线路（与线路商协商或拔测试纤）后 **30 秒内**收到 P1 邮件，恢复后收到恢复邮件；
- 探针 VM 关机后 60 秒内收到"监控盲区"告警；
- 断中心网络 1 小时后探针数据自动补传，无丢失。

### M2 测速与大屏（第 5~6 周）

- 探针测速客户端：引擎 A（Ookla 公共节点协议实现，自动就近选联通节点）+ 引擎 B（HTTP 大文件限时下载测速，URL 池后台可配），引擎可切换。
- 中心端测速调度器（24h 错峰时间表、全局串行、手动"立即测速"、失败重试）。
- P2 告警：线路降质（丢包/时延/抖动，动态基线）、带宽异常（< 契约 70% 连续 2 次）；静默窗口。
- 大屏 v1：线路状态墙、可用率曲线、告警滚动、自适应 1080P/4K、自动轮播。
- 中断自动触发 mtr 诊断并入告警邮件。

### M3 完善与报表（第 7 周）

- 告警规则可视化编辑、通知分组（按楼层/级别/收件组）、日报周报生成与邮件推送、报表导出（PDF/Excel）。
- 探针自更新（分批灰度）、操作审计日志、用户角色（管理员/观察者）。
- 性能与稳定性：中心端压测（12 探针 × 全指标 30 天模拟回放）、慢查询优化。

### M4 试运行与验收（第 8 周）

- 与现网并行试运行 7 天，每日复盘误报/漏报，调整阈值与基线。
- 故障演练清单：拔线（线路中断）、断楼层交换机（内网故障）、关探针（盲区）、断中心（缓存补传）、测速高峰压测。
- 交付物：部署手册、运维手册（含常见故障处置）、用户操作手册、验收测试报告。
- 培训：管理端使用 1 场、值班大屏使用 1 场。

验收标准：试运行 7 天可用率 99.9%+，关键故障场景全部按预期告警且无误报，文档齐备。

## 4. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 策略路由对探针源 IP 不生效/防火墙限制 | 整个探测模型失效 | M0 第一时间实验验证；备选方案：让线路商/防火墙侧为探针段单开策略，或探针逐台放楼层弱电间物理部署 |
| ICMP 被运营商或目标侧限速 | 误报丢包 | 多目标冗余 + TCPing/HTTP 兜底，单一异常不判中断 |
| 测速占用带宽影响办公 | 业务投诉 | 全局串行 + 错峰 + 限时长限并发，可按需暂停；先每 60 分钟/线灰度 |
| 公网测速节点质量波动 | 测速值异常 | 多节点择优 + 引擎 B 兜底 + 每周交叉校准 + 结果平滑 |
| 探针宿主机故障 | 监控盲区 | 盲区告警本身覆盖此场景；二期每楼层加第 2 台探针交叉验证 |
| 误报调优周期长 | 信任度下降 | 迟滞 + 冷却 + 多目标判定机制内置；试运行期每日调参复盘 |
| 邮件通道不稳定 | 漏报 | 发送重试 + 发送失败本地落盘补发 + 管理端告警中心兜底可见；二期加企业微信/钉钉双通道 |

## 5. 上线后演进方向（二期候选）

1. 防火墙 SNMP 采集 12 个 WAN 口真实流量曲线；
2. 企业微信/钉钉/短信多渠道告警与值班升级（escalation）；
3. 双探针交叉验证与探针池自动调度；
4. 楼层平面图可视化（SVG 楼层图上叠加热力状态）；
5. 线路质量月度对比报告，辅助线路商续约谈判；
6. MCP/告警智能诊断（自动汇总 mtr + 历史模式给出处置建议）。

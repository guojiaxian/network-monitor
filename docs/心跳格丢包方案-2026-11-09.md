# 心跳格丢包口径方案（2026-11-09）

> 背景：现网心跳格「橙 / 紫」语义与探针实际丢包测量能力不匹配。本文记录三个候选方案、
> 真实数据测算与最终决策。**唯一权威实现以代码为准**，本文只做决策留档。

## 0. 现状（方案实施前）

- 探针每 10 秒对每个公网 ICMP 目标发 **1 个包**，失败重试 1 次（300ms），两次都失败才记 1 条失败样本。
- 中心按 5 分钟窗口、每目标丢包率**下中位数**判定 P2 降质；心跳格：
  - 橙 = 该分钟有失败样本，但 5 分钟中位数未超阈值；
  - 紫（`#a78bfa`）= 5 分钟中位数超阈值（与 P2 同口径）；
  - 红 = 该分钟全部失败；灰 = 无样本。
- 问题：每 10 秒只有 1 个包，统计噪声大；失败重试会把真实丢包掩盖成"重试后失败率"。

## 1. 三个候选方案

### 方案 A：每轮 3~5 包，按包上报（探针侧小改）

- 每 10 秒对每个目标发 N 包，逐包上报样本。
- 优点：改动只在探针；统计精度提升。
- 缺点：中心样本量、内存环、VM 写入 ×N；心跳格橙色会因"任意一包失败"显著变多。

### 方案 B：增加 1 分钟严重丢包短窗口

- 60 秒窗口丢包 ≥50% 且连续 2 次评估成立 → 快速 P2/P1 预警。
- 优点：真正缩短严重故障发现时间。
- 缺点：要改中心告警状态机、配置、前端类型映射；与线路中断存在重复告警风险。
- 依赖：当前 10 秒 1 包时 60 秒只有 6 条样本，门槛不足，需与 A/C 配合。

### 方案 C：每轮 5 包，聚合为 1 条带丢包率的样本（最终采用）

- 每 10 秒对每个目标并发发 5 个 ICMP 包：
  - `OK` = 至少收到 1 包（保住"通/断"语义与线路判活）；
  - `LossPct` = 丢失包数 ÷ 5 × 100（真实轮丢包率）；
  - `RTT` = 成功包平均时延。
- 公网 ICMP **本轮不做逐包重试**（重试会掩盖真实丢包）；网关探测仍单包 + 重试。
- 中心 `pingRec` 记录轮丢包率，`lossStats` / `minuteStats` 改为按轮丢包率加权；
  `MinStat` 新增每分钟丢包 `L`；探测历史桶 `PL` 改用 `nw_ping_loss_pct`。
- 协议无需新增字段：`proto.Sample.LossPct` 已存在；旧探针 0/100、旧中心忽略该字段，双向兼容。

## 2. 资源测算（方案 C）

每 10 秒 5 包、2 个公网目标：

| 指标 | 现状 | 方案 C |
|---|---|---|
| 每探针包/秒（含网关） | 0.3 | 1.1 |
| 12 台合计包/秒 | 3.6 | 13.2 |
| 总带宽（约） | <5 kbps | 约 21 kbps |
| 中心 3 小时内存环 | 2.6 万条 | **2.6 万条（不变）** |
| VM 2 年磁盘 | 约 1.1 GB | **不变** |
| 5 分钟样本量/目标 | 30 包 | **150 包** |
| 精度（理论 95%） | ±10.7 个百分点 | **±4.8 个百分点** |

结论：带宽、探针 CPU、中心内存、VM 磁盘均无压力。

## 3. 真实数据测算（2026-11-09 08:18–16:18，8 小时）

- 12 台 × 2 目标，共 68,918 条公网 ping 样本，失败 1,032 条，整体失败率 1.50%。
- 5 台探针 0 失败（probe-2/4/6/7/12）；最差 probe-1 失败率 5.41%。
- 当前橙色格 366 / 5,772 = **6.3%**；8 小时内无紫色、无红色。
- 相邻两次探测同时失败的比例是独立预期的 7~17 倍 → 丢包呈**突发性**，不是每包独立随机。

方案 C 取消重试后，probe-1/10/3/8/9 的 5 分钟中位数可能超过 10%，会长期紫色并持续触发 P2 降质告警。

## 4. 最终配色与告警规则（2026-11-09 用户决策）

### 4.1 心跳格（单分钟）

```
该分钟没有任何样本                          → 灰 nodata
该分钟所有轮次 5 包全丢                      → 红 fail
该分钟两个目标丢包率下中位数 P > 阈值        → 紫 degraded
未紫，但该分钟有丢包（L>0）                   → 橙 partial
其余                                        → 绿 ok
```

- P = 该分钟各目标丢包率的下中位数；每目标至少 5 轮才参与，单目标全断时 P=0（不标紫）。
- 橙、紫都只看**单分钟**，不再有 5 分钟滚动尾巴。
- 8 小时实测：单分钟紫格约 **214 / 5,746 = 3.72%**，集中在 probe-1/10/3/8/9。

### 4.2 P2 告警（两层）

| 类型 | 触发 | 恢复 |
|---|---|---|
| 常规降质 `degraded` | **连续 3 分钟**每分钟 P > 阈值（默认 10%） | 连续 3 分钟 P ≤ 阈值×70% |
| 短时严重丢包 `loss_severe` | **单分钟** P ≥ 50% | 单分钟 P < 35% |

- 3 分钟为 `alert_settings.loss_window_min`（默认 3，可配 1~10）。
- 8 小时实测：单分钟 P>10% 的连续段共 105 段；连续 ≥3 分钟 29 次，连续 ≥5 分钟 7 次。因此常规 P2 取连续 3 分钟，既比"任一分钟"稳定，又比"连续 5 分钟"灵敏。
- 短时严重丢包单分钟 ≥50% 立即报，覆盖 1~2 分钟严重丢包；不与常规降质重复报（常规告警在途时跳过）。
- P1 线路中断期间/刚恢复 3 分钟内，P2 降质与短时严重丢包均不判定（并入中断事件）。

### 发布顺序

1. 探针先发（旧中心忽略 `LossPct`，行为不变）：构建 agent → 上传 release → probe-1 灰度 → 全量 12 台。
2. 中心再发：install server 二进制 + `restart --app-only`。
3. 前端最后：`cp web/dist`。

### 观察指标（24 小时）

- 12 台探针在线率、线路在线率、P2 降质告警数量（重点看是否出现持续紫色/告警风暴）。
- 心跳格橙/紫比例（按探针、按小时）。
- 探针 CPU / 内存（5 包突发后是否明显上升）。
- VM 写入量与磁盘增长。
- 原始轮丢包率分布（`nw_ping_loss_pct`）与旧口径失败率对比。

### 回滚

- 探针：上传旧版本 release，批量升级回 v1.0.1。
- 中心/前端：恢复旧二进制与旧 `web/dist`，`restart --app-only`。

```bash
# 1) 在线与告警

# 2) 轮丢包率分布（近 24h）
NOW=$(date +%s); START=$((NOW-86400))
curl -s "http://127.0.0.1:8428/api/v1/export?match%5B%5D=%7B__name__%3D%22nw_ping_loss_pct%22%2Cclass%3D%22public%22%7D&start=$START&end=$NOW" | \
python3 -c "
import sys,json,collections
c=collections.Counter(); per=collections.defaultdict(lambda:[0,0.0])
for line in sys.stdin:
    try:s=json.loads(line)
    except:continue
    pr=s['metric']['probe']
    for v in s.get('values',[]):
        c[v]+=1; per[pr][0]+=1; per[pr][1]+=v
print('值分布',dict(sorted(c.items())))
for pr,(n,sm) in sorted(per.items(),key=lambda x:-x[1][1]/x[1][0] if x[1][0] else 0):
    print(pr,'n=%d avg=%.2f%%'%(n,sm/n if n else 0))
"
```

判定标准：若 24h 内 P2 degraded 告警数明显高于历史（历史 8h 约 5 条、均已 resolved），或某探针平均轮丢包率接近/超过 10%，说明原始丢包被重试掩盖较多，需回滚探针或把每轮包数降为 3。

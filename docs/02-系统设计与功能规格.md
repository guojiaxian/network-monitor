# 系统设计与功能规格说明书

> 项目：单位多出口宽带网络监控系统（暂定名 **NetWatch**）
> 版本：v0.1（待评审）
> 配套文档：《01-开源项目调研报告.md》《03-开发计划.md》

---

## 1. 需求概述

单位现有 **12 条联通宽带（12 个互联网出口公网 IP）**，防火墙通过**策略路由（PBR，按源网段）**将流量分配到各线路，每层楼一个 `/24` 子网、对应一条线路。某条线路偶发中断会导致对应楼层整层无法上网。

本系统目标：

1. **实时监测**每条线路、每个楼层子网的连通性与网速；
2. **区分故障域**：楼层内网故障 vs 线路/出口故障，第一时间定位"该找线路商还是该查楼内交换机"；
3. 异常时**邮件报警**（中断、降质、恢复），防抖动、防漏报；
4. 提供 **Web 管理端**（配置、查询、告警管理）与**大屏展示**（值班室投屏）；
5. 探针部署在单位虚拟化平台，虚拟机数量不限，但**多探针的部署/调度/升级必须足够简单**。

> 注：楼层与子网的对应关系（如 1 楼 = 10.8.25.0/24、2 楼 = 10.8.26.0/24）在系统中做成**可配置映射表**，实施时以实际清单为准。

核心思路：**每台探针虚拟机的网卡接入对应楼层的子网（VLAN），其出向流量经防火墙策略路由天然走该楼层绑定的宽带线路**——探针探测的"出口连通性"与该楼层用户真实体验完全一致，不依赖对防火墙做任何改动。

## 3. 探针部署方案（关键设计决策）

由于策略路由按**源网段**生效，探针必须以楼层子网内的 IP 为源地址发探测流量。两种落地方式：

| | 方案 P1：12 台精简探针 VM（推荐） | 方案 P2：1 台探针 VM 配 12 虚拟网卡 |
|---|---|---|
| 网络条件 | 每台 VM 的 vNIC 接入对应楼层 VLAN（access 口） | 虚拟化宿主机需上联 **trunk 口**（放行全部 12 个楼层 VLAN），vSwitch 建 12 个端口组 |
| 故障隔离 | 好，单探针故障只影响一条线路的监测 | 一般，探针 OS 故障则全部盲区（可用 2 台互备缓解） |
| 源 IP 绑定 | 天然生效，无需配置 | 需在 Linux 内配 12 份策略路由（`ip rule` + 12 张路由表），agent 按 `SO_BINDTODEVICE`/源地址绑定 |
| 运维复杂度 | 由自动化消解（见下） | 单 OS，但网络配置复杂，排障难 |
| 冗余 | 后期每层加第 2 台探针即可交叉验证 | 需再克隆整台 VM |

**推荐 P1**，理由：网络侧只需给每台 VM 一个 access 口，不依赖宿主机 trunk 权限（很多单位虚拟化平台由不同部门管，改 trunk 流程长）；且配合下述自动化，"12 台 VM"的管理成本接近 1 台。

**多探针统一部署与调度（回应"多台虚拟机管理难度"关切）：**

1. **探针是单二进制 Go 程序**（约 15MB）+ systemd 服务，无任何运行时依赖；不强制 Docker。
2. **自动注册**：新 VM 首次启动仅需一条命令（预置注册 token + 中心地址），探针上报主机信息自动建档。
3. **配置中心化**：探测目标、频率、阈值、测速计划全部由中心端下发，探针本地零配置文件，改配置网页上点一下、全部探针 10 秒内生效。
4. **一键部署脚本**：配合虚拟化模板克隆 + cloud-init/首启脚本，从克隆到上线 < 10 分钟；文档提供逐台手动部署的 5 分钟操作卡。
5. **自更新**：中心端上传新版 agent 后一键推送，探针分批灰度升级。
6. **断网缓存**：探针与中心失联时数据本地缓存（≥24h），恢复后补传，杜绝"探针失联期间数据丢失"。
7. **盲区告警**：任何探针心跳中断 > 60s，中心立即发"监控盲区"P0 告警——探针自身故障不会被误判为线路正常。

## 4. 探测项与指标设计

每条线路（= 每楼层子网）的探测矩阵：

| 探测项 | 目标 | 频率 | 指标 | 用途 |
|---|---|---|---|---|
| ICMP Ping-网关 | 楼层默认网关 | 10s | 时延 min/avg/max、丢包率 | 故障域判定：网关不通=楼层内网/接入故障 |
| ICMP Ping-公网 ×3 | 223.5.5.5（阿里）、119.29.29.29（腾讯）、114.114.114.114 | 10s（错相） | 时延、丢包率、抖动 | 线路连通性，多目标防单点误判 |
| TCPing | www.qq.com:443、www.baidu.com:443 | 30s | 连接耗时、成功率 | 兜底 ICMP 被限速/禁用的情况 |
| DNS 解析 | 向 223.5.5.5 / 114.114.114.114 解析指定域名 | 60s | 解析耗时、成功率 | 验证 DNS 链路 |
| HTTP 探测 | GET 大站首页/轻量端点（默认：www.baidu.com、www.mi.com、www.qq.com、www.jd.com） | 60s | TTFB、状态码、成功率 | 端到端应用层验证 |
| **内→内 内置监控** | 中心服务器自身作为探针（Uptime Kuma 模式），监控内网服务（OA/业务系统/交换机）：TCP/HTTP/ICMP，后台自由增删 | 默认 30s/目标 | 状态、时延、HTTP 码 | 内网关键服务可达性 |
| **测速** | 直接对互联网公网测速（见 4.1） | 默认每线每 30 分钟，全局错峰串行 | 下行/上行 Mbps、时延 | 带宽劣化发现 |
| 自动诊断 mtr | 中断时自动触发 | 事件驱动 | 逐跳时延/丢包 | 报障时随邮件附上，定位断点 |

说明：
- 全部探测支持**绑定源 IP / 源网卡**，确保流量经指定线路出站。
- 探测流量总量极小（每线路 < 50kbps），测速除外（见 4.1）。
- **探测目标全部在管理后台可自由配置**（已确认的需求）：默认目标选用高稳定性的公共大站（百度、小米、腾讯、京东官网）与公共 DNS（223.5.5.5、119.29.29.29、114.114.114.114）。没有任何目标"绝对不掉线"，因此系统采用**多目标投票判定**：单目标异常不触发线路中断告警，全部/多数目标失败才判定，避免把目标的偶发抖动误报为线路故障。

### 4.1 测速方案（已确定：探针直接对互联网测速）

不建设自建测速节点，由探针直接对公网测速。采用**引擎抽象 + 多引擎**设计，中心端可配置每条线路使用的引擎与参数：

1. **引擎 A：Ookla 公共测速节点（首选）**。使用开源协议实现（如 `speedtest-go`，MIT）直接访问 Speedtest.net 的公共节点列表，**自动就近选择联通节点**，测得下载/上传/时延。不使用 Ookla 官方 CLI，规避其商用许可限制。
2. **引擎 B：公共大文件 HTTP 下载测速（兜底）**。维护一组高稳定下载源 URL 池（后台可配），分片 Range 限时下载（默认 ≤ 15s）计算吞吐；上传测速可选（POST 分片到上传端点）。
3. **调度防扰民**（不因直连公网而放松）：
   - **全局串行**：中心端调度器保证同一时刻全网只有 1 条线路在测速（每条线路上报"最近测速结果 + 预约时间片"）；
   - 默认每线每 30 分钟一次（后台可调），可避开业务高峰时段；
   - 单次测速限时（下载阶段 ≤ 15s）+ 限并发连接数；失败自动重试 1 次后放弃本轮；
   - 测速计划由中心端统一下发（24h 错峰时间表），支持网页上"立即测速"。
4. **校准**：每线每周用另一引擎交叉测 1 次，偏差 > 25% 时在报表中标注。

### 4.2 可选增强：防火墙 SNMP 采集（已实现）

防火墙开通**只读 SNMP v2c** 后，中心端直接轮询 WAN 口 64 位字节计数器（ifHCIn/OutOctets，默认 30 秒），差分计算每线**真实上下行速率**写入时序库（`nw_snmp_in/out_bps`，带 line 标签）——零测试流量成本，与测速互补（测速测能力上限，SNMP 看真实占用）。管理后台"系统设置 → SNMP"配置设备/团体字，一键拉取接口列表后按线路映射（一条线路对应一个 WAN 接口），线路详情页新增 24 小时真实流量曲线（含契约带宽参考线）。未开通 SNMP 时功能完全关闭，不影响其余能力。

## 5. 数据模型与存储

业务库（PostgreSQL）核心表：

- `floor`（楼层）：id、名称、子网 CIDR、网关 IP
- `line`（线路）：id、运营商、公网 IP、契约上/下行带宽、绑定的楼层、探针列表
- `probe`（探针）：id、名称、所在线路、版本、注册 token、心跳时间、状态
- `alert_rule` / `alert` / `silence` / `notify_group`：告警规则、告警事件、静默窗口、通知组
- `speed_plan`：测速计划
- `user`：管理端账号（管理员/观察者两角色，大屏走只读匿名 token）

时序库（VictoriaMetrics）指标（均带 `line=`, `probe=`, `target=` 标签）：

- `ping_latency_seconds{quantile}`、`ping_loss_ratio`、`ping_jitter_seconds`
- `tcp_connect_seconds`、`tcp_success_ratio`
- `dns_resolve_seconds`、`dns_success_ratio`
- `http_ttfb_seconds`、`http_success_ratio`
- `speedtest_download_mbps`、`speedtest_upload_mbps`
- `probe_up`（心跳）

**容量估算**：12 线路 × 6 探测项 ≈ 120 万样本/天，90 天保留 ≈ 1 亿样本；VictoriaMetrics 压缩后磁盘占用 < 10 GB，单中心机 4C8G 完全够用。

## 6. 告警设计（邮件报警机制）

### 6.1 告警规则（默认值，全部可配）

| 级别 | 名称 | 触发条件 | 邮件策略 |
|---|---|---|---|
| **P0 监控盲区** | 探针失联 | 探针心跳中断 > 60s | 立即发，10 分钟未恢复重复提醒 |
| **P1 线路中断** | 楼层网关正常 + 全部公网探测目标连续失败；**多探针线路需全部有效探针一致报中断（交叉验证）** | 判定为宽带线路/出口故障 | 立即发"紧急"邮件 |
| **P2 探针数据冲突** | 多探针线路中部分探针报中断、其余正常 | 线路大概率正常，优先检查异常探针 | 触发后发，冷却期内不重复 |
| **P1 楼层中断** | 楼层网关不可达 ≥ 30s | 楼层内网/接入故障（不是线路问题） | 立即发，文案与线路中断明确区分 |
| **P2 线路降质** | 近 5 分钟丢包率 > 10%；或平均时延 > 动态基线 ×1.5；或抖动 > 30ms | 线路质量劣化 | 触发后发，冷却期内不重复 |
| **P2 带宽异常** | 测速值 < 契约带宽 ×70%，连续 2 次测速 | 带宽不达标 | 发生即发，恢复后补发恢复通知 |
| **P3 提醒** | DNS 成功率低、单目标异常（其余正常）等 | 辅助信号 | 汇总进日报 |

### 6.2 告警机制要点

- **恢复通知**：所有告警恢复时发送"已恢复"邮件，注明中断时长、影响楼层。
- **防抖动**：触发需连续 N 次满足 + 恢复需连续 M 次正常（迟滞）；同一告警 5 分钟冷却期；闪断在事件流中合并为一条。
- **静默窗口**：支持按线路/楼层设置维护静默（如线路商夜间割接）。
- **通知分组**：按楼层/线路/级别绑定不同收件组（如 P0/P1 → 全体网络管理员，P2 → 值班员）。
- **IM 通道**：除邮件外支持钉钉/企业微信群机器人 webhook 推送（P0/P1 恒推、P2 按开关；钉钉支持加签），管理后台可测试；与邮件通道相互独立可并用。
- **日报/周报**：每日 8:00 发送前 24h 各线路可用率、平均时延、测速均值、告警汇总；周报含趋势对比。
- **邮件内容**：HTML 模板，含楼层、线路、公网 IP、故障开始时间、当前时延/丢包、自动 mtr 诊断结果（P1 时附）、指向管理端的详情链接。
- 可选扩展（二期）：企业微信/钉钉 webhook、短信网关。

### 7.1 首次启动向导（已确认：清单与 SMTP 均部署后在后台填写）

系统上线后通过向导完成初始化，不依赖任何预置清单：

1. 创建管理员账号 → 2. 填写 SMTP 服务器与收件组（内置"发送测试邮件"按钮）→ 3. 录入楼层/子网/线路映射（手工逐条或 CSV 导入，契约带宽选填）→ 4. 新探针注册后自动出现在"待分配"列表，管理员将其绑定到对应线路 → 5. 完成，进入总览。

### 7.2 UI 设计基准（已确认：参考并复用 Uptime Kuma）

- **协议核实**：Uptime Kuma（louislam/uptime-kuma，93k+ stars）采用 **MIT 协议**，前端栈为 **Vue 3 + Bootstrap 5 + Chart.js/vue-chartjs + vue-router + dayjs**，可合法复用其 UI 代码（保留原版权声明）。
- **前端选型调整**：管理端与大屏与 Uptime Kuma **同栈**（Vue 3 + Bootstrap 5 + Chart.js），最大化复用其组件与样式；大屏的复杂可视化（状态墙动效、趋势大图）在此基础上叠加 ECharts。
- **管理端总览页对齐 Uptime Kuma Dashboard 的设计语言**：左侧导航 + 主区监控卡片列表；每张卡片含状态色点、线路名称、当前时延、**心跳条**（分段竖条展示近期逐次探测成败，Uptime Kuma 的标志性元素）与可用率百分比；配色与明暗主题沿用其 SCSS 变量。

## 8. 大屏功能规格（值班室投屏，1920×1080 / 4K 自适应）

- **顶部**：系统名 + 实时时钟 + 全局可用率 + 在线告警数。
- **主区（约占 60%）**：12 格"线路状态墙"，每格显示：楼层名 / 线路公网 IP / 状态灯（绿·正常 / 黄·降质 / 红·中断 / 灰·盲区）/ 实时时延与丢包 / 今日测速值。红色格子呼吸闪烁并置顶。
- **左下**：24h 全局可用率与平均时延趋势曲线。
- **右下**：当前告警滚动列表（时间、楼层、类型、持续时长）。
- **辅助页轮播**：可配置轮播"单线路详情"页面（如 7 天测速趋势）。
- 无操作自动运行，自动防休眠；只读 token 访问，不暴露管理功能。

## 9. 接口概览

探针 ↔ 中心（HTTPS，token 认证）：

- `POST /agent/register` — 注册（携带机器指纹）
- `GET  /agent/{id}/config` — 拉取配置（探测目标、计划，长轮询变更通知）
- `POST /agent/{id}/metrics` — 批量上报（Protobuf/JSON，批量压缩）
- `POST /agent/{id}/heartbeat` — 心跳（携带资源状态）
- `POST /agent/{id}/events` — 上报本地事件（mtr 结果等）

管理端 REST API（会话认证）：楼层/线路/探针/规则/告警/测速/报表 CRUD + `GET /stream/overview`（SSE 实时推送总览状态）。

## 10. 技术栈与部署形态

| 层 | 选型 | 理由 |
|---|---|---|
| 探针 Agent | **Go 1.22+**（pro-bing、原生 TCP/Dial、net/http；mtr 调系统 mtr） | 静态单二进制、低资源（每台 1C1G 足矣）、跨平台 |
| 中心服务 | **Go（Gin）单服务**：接入网关 + 告警引擎 + 测速调度 + 管理 API | 与 Agent 共享协议定义，单一部署单元易维护 |
| 时序库 | **VictoriaMetrics single-node** | 单二进制免运维，PromQL 兼容 |
| 业务库 | **PostgreSQL 16** | 告警/配置/用户等结构化数据 |
| 测速 | 探针内置测速客户端（speedtest-go 协议实现 + HTTP 下载测速引擎），直接对互联网测速 | 无需自建节点，零额外部署；串行调度防扰民 |
| 前端 | **Vue3 + Bootstrap 5 + Chart.js**（管理端与大屏两个入口，同一工程，复用 Uptime Kuma MIT 组件与样式）；大屏叠加 ECharts | 与 Uptime Kuma 同栈最大化复用；中文界面 |

部署（原生为主，2026-10-26 按需求方意见调整）：中心服务器为单一业务服务器，**推荐原生 systemd 部署**——server 单二进制 + VictoriaMetrics 单二进制（各配 systemd 单元，`deploy/install-server.sh` 一键安装），PostgreSQL 用系统源安装；**Docker Compose 作为备选方案**保留（`deploy/docker-compose.yml`），适合依赖版本要求严格或需要快速重装的场景。探针 12 台精简 VM（各 1C1G/20G），单二进制 + systemd，无任何依赖。

安全：探针→中心单向 HTTPS + 每 probe 独立 token；中心仅监听内网；大屏只读 token；管理端账号密码 + 登录失败锁定；全部组件不依赖公网（探测目标除外）。

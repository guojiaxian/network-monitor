# 开源项目调研报告

> 项目：单位多出口宽带（12 条联通线路）网络监控系统
> 日期：2026-10-25
> 目的：评估 GitHub/Gitee 上可复用或可二次开发的项目，确定自研 vs 集成的技术路线

---

## 1. 需求回顾（调研评估基准）

| # | 需求 | 关键点 |
|---|------|--------|
| 1 | 实时监测 12 条联通宽带出口的连通性 | 每条线路必须**以对应楼层子网为源地址**探测（防火墙按源网段做策略路由），这是本项目的核心约束 |
| 2 | 区分故障域 | 楼层网关不通（内网/接入故障） vs 网关通但公网不通（线路/出口故障） |
| 3 | 测速 | 按线路定期测上下行带宽 |
| 4 | 分布式探针 | 虚拟机资源不限，但要求 12+ 台探针**统一部署、统一调度、统一升级**难度低 |
| 5 | Web 管理端 + 中文大屏 | 大屏需按"楼层×线路"的视角展示 |
| 6 | 邮件报警 | 中断/降质/恢复/日报，要求防抖动、防漏报 |
| 7 | 部署环境 | 单位内部虚拟化平台，内网环境，无公网依赖 |

## 2. 候选项目调研结果

### 2.1 整体平台类

**① Uptime Kuma**（https://github.com/louislam/uptime-kuma）
- 定位：单实例可用性监控，UI 优秀，支持 HTTP/TCP/Ping/DNS 探测、邮件等丰富通知渠道。
- 差距：**无原生分布式探针模式**（官方 issue #1259 多年未实现），多位置需跑多实例再聚合，无法统一调度；无测速调度；域模型是"监控项"而非"线路/楼层"；源 IP 绑定能力弱。
- 结论：**不适合做核心**；其前端为 MIT 协议（Vue 3 + Bootstrap 5 + Chart.js），最终采纳为**管理端 UI 复用基座**。

**② Zabbix + 代理（Proxy）**
- 定位：企业级监控，Proxy 分布式架构成熟，ICMP（fping）、Web 场景、邮件告警齐全。
- 差距：12 个 Proxy 各自维护配置，变更繁琐；无内置测速（需外部脚本）；大屏需外挂 Grafana；中文本地化一般；学习与定制成本高，团队后续维护门槛高。
- 结论：**可用但过重**，作为兜底选项。

**③ 夜莺 Nightingale + Categraf + VictoriaMetrics**（https://github.com/ccfos/nightingale）
- 定位：国产开源监控告警平台（Go + Vue），Categraf 内置 `input.ping` 插件（`ping_loss_percent`、`ping_result_seconds`），远端写入 VictoriaMetrics，内置告警引擎与邮件/钉钉通知，中文文档完善。
- 差距：Categraf 探针按静态配置文件定义探测目标，**中心端对探针统一调度能力弱**（每台探针逐台改配置）；无测速功能；"楼层×线路"业务视图与大屏需在 Grafana 中拼装或二开。
- 结论：**最强的"纯集成"方案**，见第 3 节方案 A。

**④ 哪吒监控 Nezha V2**（https://github.com/nezhahq/nezha）
- 定位：服务器监控面板（Go + Vue），Agent 自动注册（gRPC），"服务监控"支持从指定 Agent 发起 ICMP Ping / TCPing / HTTP 任务，告警规则 + 多渠道通知，中文生态活跃。
- 差距：域模型是"服务器监控"，改造成"线路监控"需要动核心数据结构；无测速；大屏为服务器视角；二开后跟随上游升级困难。
- 结论：架构上最接近（Agent 自动注册 + 指定 Agent 执行探测任务），**二开成本不低于自研**，且改造后与上游割裂。不推荐作为基座，但其 Agent 注册/任务下发协议设计值得借鉴。

**⑤ SmokePing**（master/slave 架构，https://oss.oetiker.ch/smokeping/doc/smokeping_master_slave.en.html）
- 定位：经典线路质量（时延/丢包）监测工具，官方支持 Master/Slave 分布式探针。
- 差距：RRD 图表风格陈旧，无测速，无现代化告警（需脚本外挂），无管理界面，Perl 技术栈二次开发困难。
- 结论：不推荐，仅作为"分布式探针测线路质量"的成熟先例参考。

**⑥ 轻量国产项目：SmartPing / ServerStatus / ping-prober**
- SmartPing（gy-games/smartping）：节点互 ping + 拓扑 + 报警，纯 ping 场景，无测速、无统一调度，项目活跃度低。
- ServerStatus：云探针面板，三网延迟展示，告警弱，无测速。
- 结论：功能覆盖不足，不做基座。

### 2.2 组件类（可复用）

| 组件 | 用途 | 评估 |
|------|------|------|
| **Uptime Kuma**（https://github.com/louislam/uptime-kuma） | **UI 复用基座（已采用）** | MIT 协议、93k+ stars、Vue 3 + Bootstrap 5 + Chart.js 栈；管理端首页复用其 Dashboard 设计语言与组件/样式代码（保留版权声明） |
| **VictoriaMetrics**（single-node） | 时序存储 | 单二进制、免运维、压缩率高、Prometheus 兼容，百万级样本/天毫无压力，免费商用 |
| speedtest-go 等开源 Ookla 协议实现 | 探针直连互联网测速 | 使用开源协议实现访问 Speedtest.net 公共节点（不用 Ookla 官方 CLI，规避商用许可限制）；HTTP 大文件下载测速作兜底 |
| **xterm.js**（https://xtermjs.org，MIT）+ gorilla/websocket | 管理后台网页 SSH 终端 | VS Code 同款终端模拟器；浏览器 xterm.js ↔ WebSocket ↔ 探针 SSH PTY，即阿里云网页终端同款架构 |
| Prometheus blackbox_exporter | 黑盒探测 | 支持 `source_ip_address` 指定探测源 IP（技术可行性已验证），但配置分散在每台探针，仅作集成方案零件 |
| speedtest-exporter（Ookla CLI 封装） | 公网测速 | 无调度/错峰能力，Ookla CLI 商用许可受限，仅作外部参考基准 |
| ECharts + Vue3 + Element Plus | 前端 | 大屏与管理端标准选型，成熟 |

### 2.3 结论

**没有任何单一开源项目同时满足：源网段策略路由探测、线路/楼层域模型、测速调度、探针统一管理、中文管理端+大屏、邮件告警。**

- 差异化核心逻辑（约占代码量 30%）必须自研：探针源 IP 绑定、线路域模型、测速调度、盲区检测。
- 成熟基础设施（约占 70%）可复用：时序存储、测速服务端、前端框架。

因此推荐 **"自研轻量平台 + 复用成熟组件"**（方案 B），备选 **"夜莺全家桶集成"**（方案 A），详见《02-系统设计与功能规格.md》。
